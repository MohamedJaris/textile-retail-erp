1. Project Purpose

This system is designed for a readymade retail store, not a textile manufacturing business. The ERP should replace disconnected registers, spreadsheets and manual stock/accounting processes with one centralized system.

Billing

Fast POS billing with barcode scanning, search, manual selection, discounts, taxes, multiple payment methods and invoice generation.

Inventory

Track stock at product/variant level, purchases, sales, returns, adjustments, low-stock thresholds and complete stock movement history.

Business Management

Manage suppliers, dealers, customers and staff from structured master records.

Finance

Track income, expenses, supplier payables, customer receivables, payments and transaction-linked accounting information.

Core objective: every important business event should create traceable records. A sale should affect the sale record, stock, payment and relevant ledger information rather than simply changing a few numbers.

2. Major Architecture Decisions

2.1 Monolith vs Microservices

Recommended: Modular Monolith. Build one Spring Boot application, but organize it into strongly separated business modules. Do not start with microservices.
OptionAdvantagesDisadvantagesDecision
Modular MonolithSimple deployment; simple transactions; one database; faster development; easier debugging; lower infrastructure cost; ideal for current store scale.Less independent scaling; application is one deployable unit.Recommended
MicroservicesIndependent scaling/deployment; team autonomy; service isolation; useful for very large SaaS systems.Network failures, distributed transactions, service discovery, queues, observability, deployment complexity and higher maintenance.Do later if required

Why not microservices initially?

The ERP contains tightly related operations. A retail sale may simultaneously create a sale, reduce stock, record a payment and update a customer receivable. In a monolith, these can be handled as one database transaction using Spring's transaction management.

Customer buys product
       ↓
Create Sale
       ↓
Create Sale Items
       ↓
Reduce Stock
       ↓
Record Payment
       ↓
Update Customer Ledger (if applicable)
       ↓
Generate Invoice

In microservices, these operations could cross multiple network boundaries. That introduces distributed transaction and failure-handling problems that are unnecessary for the initial system.

2.2 Local vs Cloud

Recommended: Cloud deployment on AWS. The ERP should be centrally hosted so authorized users can access the same data from the shop, owner's device or other permitted locations.
OptionAdvantagesDisadvantagesDecision
LocalWorks without internet; low latency; no recurring cloud hosting cost; data can remain on-site.Single-machine failure risk; backups become a local responsibility; remote access is harder; updates must be managed on-site.Possible for offline-first environments
CloudCentralized data; remote access; backups; easier maintenance; easier multi-user/multi-branch expansion; centralized monitoring.Internet dependency; hosting cost; requires security and backup strategy.Recommended

2.3 The final choice

React.js
   ↓
REST API
   ↓
Spring Boot Modular Monolith
   ↓
PostgreSQL
   ↓
AWS Cloud
POS availability consideration: Internet failure can interrupt a cloud POS. Version 1 can require a reliable connection. If uninterrupted billing is later a hard business requirement, add an offline-capable POS/local cache and synchronization layer rather than prematurely complicating the entire ERP.

2.4 Why Modular Monolith + Cloud is the sweet spot

  • Fastest practical development path.
  • Simple and reliable financial/inventory transactions.
  • Easy deployment compared with many independent services.
  • Centralized database and backups.
  • Easy access for multiple authorized users.
  • Can be made microservice-ready through clean module boundaries.
  • Supports future multi-store growth without forcing microservice complexity today.

4. Product Management

The product system must reflect how readymade retail actually sells goods. Colour is intentionally excluded because the store does not require a colour field.

4.1 Product and Variant separation

Use a parent product and variants when size or another sellable attribute changes stock independently.

Product: Formal Shirt
│
├── M   → SKU: SH001-M  → Stock: 12
├── L   → SKU: SH001-L  → Stock: 8
├── XL  → SKU: SH001-XL → Stock: 5
└── XXL → SKU: SH001-XXL → Stock: 2

4.2 Product fields

Size / VariantSellable variant such as M, L, XL, 32, 34, etc., where applicable.

4.3 Product identity rules

  • Database ID: technical identity.
  • SKU: business identity/search identifier.
  • Barcode: physical machine-readable identifier.
  • Never make barcode generation the foundation of billing.
  • A product can be found by barcode, SKU, name, category or manual selection.

4.4 Product lifecycle

Create Product→Create Variant→Set Price/Tax→Register/Generate Barcode→Save→Optional Label Print

5. Barcode Generation, Registration & Reading

Barcode is an input mechanism, not the billing engine.

5.1 Supported barcode scenarios

  • Existing supplier/manufacturer barcode: store it against the product variant.
  • System-generated barcode: generate an internal barcode when a product does not have one.
  • Manual entry: cashier can type a barcode.
  • Scanner entry: USB/Bluetooth scanners can behave like keyboard input.
  • SKU search: billing continues even without barcode.
  • Name/category search: useful when a physical barcode is unavailable or damaged.
  • Camera scanning: can be a future feature.

5.2 Barcode uniqueness

Every active barcode should map to one unambiguous sellable variant. The backend must validate uniqueness rather than relying on the frontend.

5.3 POS barcode behavior

Scanner / Manual Barcode / SKU / Search / Category
                    ↓
             Product Resolver
                    ↓
                  Cart
                    ↓
          Pricing + Discount + Tax
                    ↓
                 Payment
                    ↓
                Invoice
                    ↓
         Stock + Accounting Impact

5.4 Label printing

Optional label printing can show product name, SKU, price and barcode. The ERP should not assume that every store needs to print labels.

6. Dynamic Billing / POS Engine

The billing system must be versatile and configurable rather than hard-coded around barcode scanning.

6.1 Universal cart

Regardless of how a product is selected, the POS should create the same cart line structure. This makes barcode scanning, manual search and future integrations share one billing engine.

6.2 Transaction types

  • Normal retail sale
  • Credit sale
  • Dealer / bulk sale
  • Sales return
  • Exchange
  • Future configurable transaction types

6.3 Payment methods

  • Cash
  • UPI
  • Card
  • Bank transfer
  • Credit
  • Split payment

Example: a ₹2,500 bill can be paid as ₹1,000 cash + ₹1,000 UPI + ₹500 card.

6.4 Discounts

  • Fixed amount discount.
  • Percentage discount.
  • Item-level discount.
  • Bill-level discount.
  • Customer-specific pricing/discount.
  • Dealer-specific pricing/discount.

6.5 Billing controls

  • Prevent selling more than available stock unless an authorized configuration permits it.
  • Require a customer for credit transactions.
  • Restrict price overrides to authorized users.
  • Restrict high-value discounts to authorized users.
  • Maintain invoice numbering.
  • Record the cashier/user responsible for each transaction.
  • Restrict bill cancellation and maintain audit records.

6.6 Sale transaction principle

A sale is more than an invoice. It is a business event that should affect sale records, sale items, stock movements, payment records and, where applicable, customer/dealer ledgers.

7. Supplier, Dealer & Purchase Management

7.1 Supplier master

  • Name / business name
  • Contact information
  • Address
  • GST/tax information where applicable
  • Payment terms
  • Outstanding payable
  • Purchase history
  • Payment history

7.2 Purchase entry

A purchase should record supplier, products/variants, quantities, purchase prices, taxes, discounts, supplier invoice reference and payment status.

Supplier→Purchase Invoice→Purchase Lines→Confirm→Stock Inward→Supplier Payable→Supplier Payment

7.3 Stock impact

Stock should increase when the purchase/stock-in transaction is confirmed. Draft or cancelled purchases should not silently increase available stock.

7.4 Dealer management

Dealers can be modeled separately when their commercial relationship differs from suppliers or retail customers. The system can support dealer-specific pricing, discounts, credit terms and transaction history.

10. Accounting — Income & Expenses

10.1 Income

  • Retail sales.
  • Dealer/bulk sales.
  • Customer outstanding payments.
  • Other income categories.

10.2 Expenses

  • Rent.
  • Electricity.
  • Staff-related expenses.
  • Transport.
  • Maintenance.
  • Miscellaneous.
  • Custom expense categories.

10.3 Supplier payments

Supplier payments should be linked to supplier outstanding and the relevant purchase/ledger records where appropriate.

10.4 Payment reconciliation

Cash, UPI, card and bank transfer should be separately identifiable so management can compare system totals with actual payment-channel totals.

10.5 Profit calculation

Do not calculate profit as simply “sales − expenses.” Product cost and stock movement must be structured so gross profit can be calculated correctly. Operating expenses can then be considered separately.

11. Returns & Exchanges

11.1 Sales return

Original Invoice→Select Items→Validate Rules→Return Qty→Stock Increase→Refund / Credit→Accounting Adjustment

11.2 Exchange

Exchange is a linked combination of returning the old product and selling/issuing the replacement product.

  • New product price higher → collect difference.
  • New product price lower → refund difference or issue store credit according to policy.
  • Equal value → no additional payment.
  • Stock must increase for the returned item and decrease for the replacement.

11.3 Return policy controls

  • Return window.
  • Whether original invoice is mandatory.
  • Item condition requirements.
  • Allowed refund methods.
  • Whether certain categories are non-returnable.
  • Who can authorize exceptions.

13. Roles, Permissions & Security

RoleTypical access
Admin / OwnerFull system access, configuration, users, accounting, reports and sensitive operations.
ManagerSales, inventory, purchases, customers, staff and reports; restricted sensitive configuration.
CashierPOS, barcode/search, payments and permitted returns; no unrestricted accounting/master-data access.
Inventory StaffStock inward, adjustments and product lookup; restricted financial controls.

Permissions should be granular enough to control sensitive actions such as changing prices, applying high discounts, cancelling invoices, editing expenses and performing stock adjustments.

Security foundation

  • Spring Security.
  • JWT or secure session strategy based on deployment requirements.
  • Backend authorization; frontend hiding buttons is not sufficient.
  • Password hashing.
  • Input validation.
  • Audit logs for sensitive actions.
  • Secure API access over HTTPS in cloud deployment.
  • Database credentials stored securely, not hard-coded.

Key relationships

  • Product 1 → many Product Variants.
  • Variant 1 → many Product Identifiers.
  • Variant 1 → many Stock Movements.
  • Sale 1 → many Sale Items.
  • Sale 1 → many Payments.
  • Purchase 1 → many Purchase Items.
  • Supplier 1 → many Purchases.
  • Customer 1 → many Sales and Ledger Movements.
  • Return 1 → many Return Items.

Stock design principle

Current stock can be maintained for fast reads, but every stock change should create a movement record. This gives the system traceability for purchases, sales, returns and manual adjustments.

19.3 Architecture principles to preserve

  • Barcode is not the primary database identity.
  • Billing is independent of barcode generation.
  • Business modules have clear boundaries.
  • Stock changes are represented as movements.
  • Customer and supplier balances are ledger-driven.
  • Financial and inventory operations are transactional.
  • Backend permissions enforce security.
  • Important actions are auditable.
  • Configuration is preferred over hard-coded business rules.

20. Final Project Definition

Final recommended product:

A cloud-hosted, modular-monolith Readymade Retail ERP built with React.js, Java/Spring Boot and PostgreSQL, deployed on AWS. It provides a dynamic POS independent of barcode generation, barcode-based product lookup, product/variant management without a colour field, inventory, purchasing, supplier/dealer management, customer credit and history, staff management, accounting, returns/exchanges, dashboards, reports and granular role-based access.

Final recommendation in one sentence

Build it as a Modular Monolith, deploy it in the Cloud, keep the POS transaction engine independent of barcode technology, and design clean module boundaries so microservices can be introduced later only if the business genuinely requires them.

Implementation quality requirements

  • Use DTOs rather than exposing database entities directly through APIs.
  • Use service-layer business logic and transactional boundaries.
  • Validate all critical inputs on the backend.
  • Use database constraints for uniqueness and referential integrity.
  • Use audit logs for sensitive changes.
  • Provide automated tests for stock, billing, payment, return and accounting rules.
  • Design backups and recovery before production launch.
  • Use HTTPS and secure secret management in AWS.
  • Monitor application errors and database health.
  • Keep business rules configurable where practical.
Important scope note: This document is a complete planning and architecture baseline, not a claim that every accounting/tax rule has already been finalized. Before production use, local GST/tax, invoicing, statutory accounting and data-retention requirements should be reviewed and implemented according to the store's actual business and compliance needs.
